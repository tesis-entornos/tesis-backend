## Module: Redis cache (stage 3)

Declared change of the reference application: a cache-aside Redis cache for item reads.

| # | Change | Reason |
|---|--------|--------|
| C1 | Dependency `redis>=8.1.0,<9.0.0` (redis-py 8.1.0 locked, no transitive dependencies). | Redis client (works with ElastiCache, `rediss://` for TLS). |
| C2 | Settings `REDIS_URL` (optional; without it the cache is disabled), `CACHE_TTL_SECONDS` (60) and `CACHE_KEY_PREFIX` (default `tesis` until D3; now required with `REDIS_URL`). | Same image for every environment; the prefix lets several environments share a cluster without key collisions. |
| C3 | `app/core/cache.py`: JSON cache with one *epoch* counter per namespace inside every key; invalidation = `INCR` of the epoch. Fail-open: any Redis error is logged and the request is served from the database. 0.5 s socket timeouts. | Cache-aside without pattern deletes; safe against concurrent readers storing values computed before a write. Fail-open keeps the cache from being a single point of failure. |
| C4 | `app/core/cache_invalidation.py`, registered in `app/main.py`: SQLAlchemy session listeners mark the `items` namespace when a flush or a bulk statement touches `Item` (or deletes a `User`) and invalidate it **after commit** (discarded on rollback). | Covers every write path, including `crud` helpers, ORM cascades and the bulk `DELETE` used when deleting a user, without touching the write routes. |
| C5 | `app/api/routes/items.py`: `GET /items/` and `GET /items/{id}` read through the cache (`CacheDep` in `app/api/deps.py`) and return the header `X-App-Cache: HIT \| MISS \| BYPASS` (not `X-Cache`, which CloudFront sets on every response). Permission checks run on every request, also for cached items; 404s are not cached. Write routes are unchanged. Response bodies are unchanged. | Makes the cache behavior observable (tests and the experiment) without reading Redis internals. |
| C6 | `compose.yml`: `redis:7.2-alpine` service with healthcheck; backend waits for it. `.env.example` documents the new settings. | Local emulation, closest to ElastiCache Redis OSS 7.x. |
| C7 | Tests: `tests/core/test_cache.py` (disabled, unreachable/fail-open, hit + invalidation, TTL) and `tests/api/routes/test_items_cache.py` (MISS→HIT, invalidation on update, delete, create and owner deletion, permissions on cached items, BYPASS when Redis is unavailable). `tests/conftest.py` gains a `redis_client` fixture. Tests use random ids and their own key prefixes; no `FLUSHALL`. | Coverage of the new module against a real Redis, without dependence on residual data. |

## Module: file storage on S3 (stage 3)

Declared change of the reference application: endpoints to upload, list, download and delete files stored in S3.

| # | Change | Reason |
|---|--------|--------|
| S1 | Dependencies `boto3>=1.43.123,<2.0.0` and, for type checking only, `boto3-stubs[s3]` (dev). | Official AWS SDK; stubs keep `mypy --strict` passing. |
| S2 | Settings `S3_BUCKET` (optional; without it `/files` answers 503), `S3_KEY_PREFIX`, `AWS_REGION`, `S3_ENDPOINT_URL` and `S3_FORCE_PATH_STYLE` (local emulator only), `MAX_UPLOAD_BYTES` (10 MiB). Credentials always come from the default AWS chain (ECS task role in AWS); they are never read from `.env`. | Same image for every environment; the key prefix lets several environments share a bucket. |
| S3 | Model `File` (`id`, `filename`, `content_type`, `size`, unique `s3_key`, `created_at`, indexed `owner_id` with `ON DELETE CASCADE`), `FilePublic`, `FilesPublic`; relationship `User.files` with cascade, like `User.items`. Migration `e3acbde9bd2f_add_file_table` (autogenerated; `created_at` typed `sa.DateTime(timezone=True)` like upstream migrations). | Metadata in Postgres allows per-user listing and pagination with the same permission rules as items, without listing S3. |
| S4 | `app/core/storage.py`: `FileStorage` (put, streamed get, delete, best-effort batch delete), botocore timeouts and standard retries; keys `{S3_KEY_PREFIX}files/{owner_id}/{file_id}` (user file names are never part of a key). The application never creates buckets. | Isolates S3 access; in AWS the bucket is created by infrastructure code. |
| S5 | `app/api/routes/files.py` (`/api/v1/files`): `POST /` (multipart, 413 above the limit), `GET /` (own files; superusers see all), `GET /{id}` (streamed through the backend, `Content-Disposition: attachment` with RFC 5987 file name, `X-Content-Type-Options: nosniff`), `DELETE /{id}`. 404/403 like items; storage errors → 502. Order of operations: upload = object then row (the object is removed if the row cannot be stored); delete = object then row. | Metadata never points to a missing object; `nosniff` + attachment prevent rendering user supplied content in the app origin. |
| S6 | `app/api/routes/users.py`: `DELETE /users/{id}` and `DELETE /users/me` delete the user's objects **after** the commit (best effort, failures logged). Uses an optional storage dependency so deleting users keeps working without S3. | Avoid orphan objects when a user is deleted (their file rows are removed by the cascade). |
| S7 | `compose.yml`: `motoserver/moto:5.2.5` (S3 emulator, host port 5050 because 5000 is often taken on macOS) and a one-shot `s3-init` (`amazon/aws-cli:2.39.3`) that creates the bucket; the backend waits for it and gets fake credentials (`test`/`test`) for the emulator. | Local emulation without AWS resources or credentials. |
| S8 | Tests `tests/api/routes/test_files.py`: round trip with byte comparison and a non-ASCII name, size limit (at and above), listing visibility, 403/404, user deletion (admin and self) removes objects, 502 with no metadata when storage is unreachable, 503 when not configured. `tests/conftest.py` deletes the objects of remaining files in its final cleanup. | Coverage of the new module against the emulator, without residual data in the bucket. |

## Test cleanup

| # | Change | Reason |
|---|--------|--------|
| T1 | `tests/conftest.py` + new `tests/utils/cleanup.py`: upstream's session fixture deleted **all** items and users at the end of the run (and S8 extended it to all file objects). Now a SQLAlchemy `after_flush` listener records the ids of every `User`, `Item` and `File` inserted during the run (by the app through `TestClient` or by test helpers), and the final cleanup deletes only those: S3 objects first, then file rows, items and users. Verified by seeding a user with an item and a file plus a superuser item, running the suite twice, and checking that counts and seeded rows/objects were unchanged. | Running Pytest against a database that holds other data (e.g. a shared, fixed environment) must not destroy that data, and the suite must not depend on an empty database. Known remaining effects on pre-existing data: the superuser password is changed and restored by `test_update_password_me`, and if `EMAIL_TEST_USER` already exists its password is reset by the `normal_user_token_headers` fixture (both are upstream behavior). |

## Deployment readiness (stage 4)

| # | Change | Reason |
|---|--------|--------|
| D1 | Settings `DB_POOL_SIZE` (3) and `DB_MAX_OVERFLOW` (2) passed to the engine (`app/core/db.py`, `build_engine`), which keeps `pool_pre_ping=True`. New `scripts/start.sh` (image `CMD`) runs `fastapi run --workers "${WEB_CONCURRENCY:-2}"` instead of a fixed `--workers 4`. Compose and `.env.example` expose the three values. Tests `tests/core/test_db.py`: the pool uses the configured sizes, and a pooled connection terminated by the server (`pg_terminate_backend`) is replaced on the next checkout. | Upstream opened up to 4 × (5 + 10) = 60 connections per task. RDS is shared by several environments, so connections per task (workers × (pool + overflow)) must be sized per environment; the defaults give 10. Pre-ping lets the pool survive a database restart or recreation. |
| D2 | `GET /api/v1/utils/ready` (`app/api/routes/utils.py`): `SELECT 1` on the engine and `HeadBucket` on the configured bucket (`FileStorage.check_bucket`); 200 `{"status": "ready", "checks": {"database": "ok", "storage": "ok"}}`, otherwise 503 with `"error"` or `"not_configured"` per check. Redis is not checked. `health-check` is unchanged. Engine injected through `get_engine` (`app/api/deps.py`) so tests can replace it. Tests `tests/api/routes/test_utils.py`: health check, ready, database unreachable, storage unreachable, missing bucket, storage not configured. | The load balancer / ECS must not route traffic to a task that cannot reach its database or bucket; the health check only proves the process answers. The cache is fail-open, so Redis being down must not take tasks out of service. A missing bucket configuration counts as not ready because every environment of the experiment uses S3. |
| D3 | `CACHE_KEY_PREFIX` has no default; `Settings` fails if `REDIS_URL` is set and the prefix is missing or empty. `compose.yml` requires it (`${CACHE_KEY_PREFIX:?}`), `.env.example` uses `tesis-local`. Tests `tests/core/test_config.py`. | ElastiCache is shared by the environments of an account; a forgotten prefix would silently mix the cache of two environments (and break the cache tests of both). Failing at startup makes the mistake visible. |
| D4 | `tests/api/routes/test_login.py::test_recovery_password` now patches `app.api.routes.login.send_email`; `tests/api/routes/test_users.py::test_create_user_new_email` patches `app.api.routes.users.send_email` instead of `app.utils.send_email`. Assertions unchanged. | Both routes import `send_email` by name, so upstream's patch did not apply and the tests opened real SMTP connections to `smtp.example.com` (the failure was swallowed by the `emails` library). Tests must not depend on external network access. |
| D5 | `Dockerfile` split in stages: `builder` (uv, runtime dependencies only: `uv sync --no-dev`), `test` (adds the dev group and copies `tests/`) and `runtime` (default, last stage: copies `/app` from `builder` onto a clean base, without uv, user `app` uid/gid 10001, files owned by root). Base images pinned by digest (`python:3.14@sha256:22caa054…`, `ghcr.io/astral-sh/uv:0.9.26@sha256:9a23023b…`). `compose.yml`: `prestart` and `backend` build/run the `test` target (`BACKEND_TEST_IMAGE`, default `tesis-backend:test`); every service image pinned by digest (`adminer` was unpinned, now `5.4.1`). Supersedes B7 for the `test` target; the `runtime` image still has no `tests/`. | The deployable image must contain only what runs in production and must not run as root. Tests need the dev tools, so they get their own target built from the same `builder` stage (same dependency versions). Digests make every build use exactly the same base layers; tags can be moved upstream. |
